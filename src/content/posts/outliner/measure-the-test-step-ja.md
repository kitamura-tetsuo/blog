[Outliner #6004](https://github.com/outliner-online/outliner/pull/6004)を読んで意外だったのは、CIジョブが遅いという事実だけでは、分かることが少ないという点でした。ジョブが10分以上かかっても、その中でテストが10分動いていたとは限りません。私は、テスト分割を検討する価値のある対象を探す監視処理を確かめていました。この違いによって、判断に使える証拠も変わります。依存関係の取得や実行環境の準備には時間がかかります。でも、テストを分割しただけで、その準備まで分担できるわけではありません。

マージ済みの変更を、公開ソースとActionsの実行記録でたどりました。ここで書くのは、その確認の記録です。私が修正を実装した、あるいはマージしたという話ではありません。以前の監視処理は、準備が大半を占めるジョブや、すでに使われなくなったPRの試作ジョブを、個別の改善候補として通していました。[PRの証拠と回帰検証の記録](https://github.com/outliner-online/outliner/pull/6004)では、#5998〜#6001を準備のみ、または証拠不足のケース、#6003を廃止済みで検証できないケースとしています。長い所要時間は、時間がかかった証拠ではあります。ただ、この監視処理が知りたいことへの答えとしては、範囲が広すぎました。

## 時計を当てる境界を決める

[マージ時点の候補判定コード](https://github.com/outliner-online/outliner/blob/a8f4d0546b62090981e957019182874d29232f32/scripts/ci_duration_monitor.py)が使うのは、GitHub自身が記録したジョブとステップの開始・終了時刻、そして成否です。Vitestのログから時間を抜き出したり、テストレポーターのJSONを必須にしたり、準備と実行が混ざったジョブの何割がテストだったかを推測したりはしません。設定された、準備から分離済みのテスト実行が成功して終わり、600秒以上かかり、ジョブの実行時間の半分以上を占める必要があります。ワークフローのパス、有効なワークフローであること、マトリクスの対象、正確な実行ステップ名、ソース上の実行契約も照合します。見慣れた表示名だけでは、何が動いたかは確定しません。

最後の確認が必要なのは、「Run server tests」という名前でも、コマンドの内側で準備を呼んでいる可能性があるからです。[マージ時点のサーバーワークフロー](https://github.com/outliner-online/outliner/blob/a8f4d0546b62090981e957019182874d29232f32/.github/workflows/ci-test-server.yml)では、準備を`Prepare server test runtime`という独立したステップに置き、実行ステップで`npm run test:prepared`を呼びます。準備を省くことなく、測る境界を移しています。ユニットテストとブラウザーテストには、もともと準備と実行の境界があり、テストコマンドも通常のリトライも維持されます。測定対象のステップ内で成功に至ったリトライは、実際に行ったテストの一部です。推測で差し引く時間ではありません。

過去について言えることにも、同じ制約があります。新しいワークフローで正しく分離できたからといって、古いサーバー用ラッパーの所要時間が、さかのぼって純粋なテスト時間になるわけではありません。欠けた証拠や混在した証拠は、証拠不足のままです。準備に調査の価値があっても、遅いというだけでテスト分割の推奨対象にはなりません。

## 候補の判定と重複の確認を分ける

もう一つ、表からは見えにくい境界も確認しました。測定結果が条件を満たすかどうかと、Issueを作るかどうかは別の判断です。#6004は、既存の識別情報、未完了Issue、証拠マーカー、消費済みの準備完了状態、クローズ後の確認よりも前に、候補判定を記録します。これらの重複防止は維持されています。すでにキューにある#5995、#5996、#5997を新しいIssue群で置き換える変更でも、シャーディングを実装する変更でもありません。正当に遅いテスト群が見つかっても、既存のIssueに結び付くのは自然な結果です。一方、証拠不足の測定結果は、そもそも候補の条件を満たしていません。その却下を重複抑止の結果と説明することはできません。[PR](https://github.com/outliner-online/outliner/pull/6004)には、この区別と、クローズ済みの誤検出に対する回帰検証が記録されています。

ネイティブの[PR検証ジョブ](https://github.com/outliner-online/outliner/actions/runs/44893209592/job/136813270300)は成功し、ログには41テストの実行と`OK`が残っています。これは、テストした範囲での収集とIssue照合の動作を裏付けます。PRイベントではレポート用ジョブがスキップされていたため、実際のAPIを使う定期収集まで完了できる証拠には、まだなっていませんでした。

最初の実際の[定期実行44971975341](https://github.com/outliner-online/outliner/actions/runs/44971975341)で、その限界が具体的になりました。[検証ジョブ137053532758](https://github.com/outliner-online/outliner/actions/runs/44971975341/job/137053532758)は、こちらも41テストすべてに成功しています。一方、[レポート用ジョブ137053580559](https://github.com/outliner-online/outliner/actions/runs/44971975341/job/137053580559)は失敗しました。公開ログには、それ以前のHTTP 502に対する読み取りリトライの警告があり、最後はHTTP本文の受信中の`IncompleteRead`エラーで終わっています。この順序は確認できます。ただし、その最後のエラーメッセージから、失敗した正確なエンドポイントやネットワーク障害の根本原因までは特定できません。

レポートの失敗は、条件を満たす候補がゼロだったという意味ではありません。この実行では、レポートの完了結果を確定できなかったということです。次の検討としては、安全な読み取りに回数を限ったリトライを設け、送達が不明になり得る書き込みとは扱いを分ける方向が考えられます。これは調査候補であり、#6004で実装済みと確認した内容ではありません。今回残せる結果は、もう少し限定的です。マージされた方針は、時間についてより適切な問いを立て、記録されたテストは通り、最初の定期レポートはなお失敗しました。この三つを一緒に残すことも、正直に測る作業の一部です。
